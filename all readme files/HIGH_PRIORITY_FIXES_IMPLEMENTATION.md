## ✅ Fix #1: Per-Store Sale ID Sequence

### **Problem**
Sales IDs were globally unique across all stores, making it impossible to identify which sale belongs to which store by ID alone. This created confusion for multi-store operations and poor UX (Store 1 might have IDs like 45, 97, 203 instead of 1, 2, 3).

### **Solution Implemented**

#### **Database Changes**
Created migration file: `database/add_per_store_sale_ids.sql`

**What it does:**
1. Adds `sale_number_store` column to sales table (INTEGER, NOT NULL)
2. Creates function `get_next_sale_number(p_store_id)` to get next sequential number
3. Creates trigger `trigger_set_sale_number_store` to auto-generate on INSERT
4. Backfills existing sales with sequential numbers per store
5. Adds unique constraint: `(store_id, sale_number_store)` must be unique
6. Adds index for performance: `idx_sales_store_number`

**Example Result:**
```
Store 1: Sale #1, Sale #2, Sale #3...
Store 2: Sale #1, Sale #2, Sale #3...
```

#### **Code Changes**
- Updated `app/api/sales/route.ts` with comments explaining the new field
- The field is auto-generated by the database trigger (no API changes needed)
- Old `sale_number` field (SALE-timestamp) is kept for backward compatibility

## ✅ Fix #2: Supplier Info Validation

### **Problem**
When adding stock with partial payment (amount_paid < total_cost), supplier information was optional. This resulted in missing supplier details in the ledger, making it impossible to track who is owed money.

### **Solution Implemented**

#### **Code Changes**

**File 1: `components/AddStockModal.tsx`**
- Added validation before creating stock batch
- Checks if `amountPaid < totalAmount`
- If true, requires `supplier_phone` to be filled
- Shows error: "Supplier information is required when making partial payment"

**File 2: `components/RestockModal.tsx`**
- Added same validation logic
- Prevents submission if partial payment without supplier info
- Clear error message to guide user

## ✅ Fix #3: Product Names in Expenses

### **Problem**
Expenses showed batch numbers (e.g., "PROD-20251230-001") instead of human-readable product names, making the expenses list confusing and hard to read.

### **Solution Implemented**

#### **Database/API Changes**

**File 1: `app/api/expenses/route.ts`**
- Updated GET query to join with `stock_batches` and `products` tables
- Query now includes:
  ```sql
  stock_batches!expenses_batch_id_fkey (
    batch_number,
    products (
      id,
      name,
      sku
    )
  )
  ```
- Processes response to add `product_display` field
- Format: "Product Name (SKU)" or "Batch XXXX" if no product found

**File 2: `app/dashboard/expenses/page.tsx`**
- Added `product_display`, `product_name`, `product_sku` to Expense interface
- Updated table display to show product info below description
- Format: 
  ```

  Product: iPhone 14 Pro (IPH14PRO)
  ```

## 🐛 Potential Issues & Solutions

### Issue 1: Migration Fails on Existing Data
**Symptom**: Error during backfill step  
**Solution**: 
```sql
-- Check for NULL store_ids
SELECT COUNT(*) FROM sales WHERE store_id IS NULL;

-- If found, fix them first
UPDATE sales SET store_id = 1 WHERE store_id IS NULL;
```

### Issue 2: Duplicate Sale Numbers
**Symptom**: Unique constraint violation  
**Solution**: This shouldn't happen with the trigger, but if it does:
```sql
-- Manually reset sequence for a store
UPDATE sales 
SET sale_number_store = NULL 
WHERE store_id = X;

-- Run backfill again for that store
```

### Issue 3: Supplier Validation Too Strict
**Symptom**: Users can't add stock even with full payment  
**Solution**: Check the comparison logic:
```typescript
if (amountPaid < totalAmount && !formData.supplier_phone) {
  // Only triggers if BOTH conditions are true
}
```

### Issue 4: Product Names Not Showing
**Symptom**: Expenses still show batch numbers  
**Solution**: 
- Check if `expenses` table has `batch_id` column
- Verify the foreign key: `expenses_batch_id_fkey`
- Check if the join is working in API response
